PuTTY URL handler test

Key authentication comes from your saved PuTTY sessions. The handler matches the host in the URL against them and launches -load <session>, so the session's key, username and port all apply. No change to your server is needed — the ssh://<host> links the monitor page already emits match on their own.

1. Should load a saved session (key auth, no password prompt)

LinkMatchesPuTTY gets
ssh://iotdata-rem-b827eb20b3d4.local HostName-load "iotdata-rem-b827eb20b3d4"
ssh://iotgate.local HostName-load "iotgate"
ssh://iotdata-master.local HostName-load "iotdata-master"
putty://iotgate session name-load "iotgate"
putty://bastu session name-load "bastu"
ssh://192.168.75.129 HostName-load "__local__"

2. Several sessions on one host, told apart by port

All six branna.net sessions share a hostname and differ only by port.

LinkPuTTY gets
ssh://branna.net:8893-load "branna-iotgate"
ssh://branna.net:9091-load "branna-bastu"
ssh://branna.net:8890-load "branna-badtuna"
ssh://branna.net:9988-load "branna-workshop"
ssh://branna.net no port given, so the first host match wins — -load "branna-adsb". Ambiguous by nature; link the port if you care which.

3. Overrides still work on top of a session

LinkPuTTY gets
ssh://matt@iotgate.local -load "iotgate" -l "matt" — session's key, different user
ssh://iotgate.local:2222 -load "iotgate" -P "2222"

4. No saved session — plain connection, expect a login prompt

  • ssh://unknown-host.example.com → -ssh "unknown-host.example.com"
  • ssh://root@unknown.example.com:2222 → -ssh -l "root" -P "2222" "unknown.example.com"

5. Hostile input — must be refused, not run

  • ssh://-pw hunter2 — smuggled PuTTY switch
  • ssh://host; calc.exe — shell metacharacters
  • ssh://127.0.0.1:99999 — port out of range
  • ssh:// — no host

6. Other protocols

  • telnet://iotgate.local:23 — -telnet
  • rlogin://vader.local — -rlogin
